## 0. 一句话重新定义产品

**给网文作者的 C 端创作工具：你给方向，它把一整个世界跑起来，从世界里长出一本书；
就算你不跑世界，它也能按大纲替你写完一本。**

- 定位不是「AI 帮你写句子」，而是**「世界 → 事件 → 正文」的流水线**。
- 两条腿必须都有：
  - **A 涌现模式**（差异化护城河）：推演回合 → 角色自己说话做事 → 成文席渲染
  - **B 直写模式**（保底可用）：没有推演、没有场景，照样按大纲/一句话写完一章
- **当前问题：两条腿都没走完一公里。** 全书累计正文 **286 字**，还没写完过一章。

## 2. 核心诊断：五个断裂

> 这五条是「为什么有这么多功能却写不出一章」的根因。每条都有代码/数据证据。

**F1 · 成文席被降级成「段落生成器」**
原设计（`agent职责与prompt设计.md` §1）：「成文 = 事件流 → 小说正文（旁白/环境/动作/心理/打斗）」，
即**渲染一场**。实现是 `engine/prose.py::_DRAFT_PROMPT` 写死「中文，150-220 字」。
→ 一场戏天然只有一段，永远长不出一章。**这就是「200 字太少」的根因，不是模型不行。**

**F2 · 章级上下文从未进入写手**
`chapters` 表有 `tone / tension_curve / word_target`，主笔 prompt 也要求产出这些；
但 `prose.py` 的写手 prompt **一个都没有**（grep 全文只有一行历史注释提到 tone）。
→ 写手不知道「这一章要完成什么、多少字、什么基调」，只能盲目写一段。

**F3 · 场景设定空着也照写**
真实书场景设定填充 **0/3**（舞台/本场目标/内容描述全空）。写手只能自由发挥，
体检随后抓到「本场设定栏全空；主角指代与猎/被猎立场倒置，结尾跳步」——**这是必然结果**。
（v1.44 已让 prompt 显式标注「未填 · 不要编造」，但**没人负责把它填上**。）

**F4 · 涌现 → 成文的桥太细**
只喂了两样：灵感池里「已采纳的高光」+ 最近一个回合的 `reasoning`。
导演产出的事件流、关键转折、张力曲线、收束汇报**没有结构化传给成文席**。
→ 推演跑了 19 回合，成文只用到其中两小撮，「涌现」的价值大部分被丢掉。

**F5 · 改稿回路不闭合**
体检/质检/润色/定点修复产出 `pending` note，采纳靠人工点；采纳后**不自动记账、不自动复检**。
→ 「改 → 验 → 记」断成三段，作者要手动串，且账本会滞后于正文。

## 3. 分工是否正确

### 3.1 业界共识的分工

长篇生成的主流做法是 **planner → writer → critic/refiner + 长程状态**（三层 + 一个状态库），
不是「一个 agent 全包」。你们原来的四席（主笔/导演/角色/成文）**方向是对的**，
甚至比多数开源项目更讲究（把「结构/调度/演绎/渲染」分开，且禁「导演写台词」）。

### 3.2 问题不在分工，在职责落位

| 席 | 现状 | 应该是 | 差距 |
|---|---|---|---|
| **主笔**（结构） | 排骨架（章/场/伏笔） | 结构 + **章级编排**（每场功能/字数/基调/伏笔埋收点），并**注入成文** | 章级字段落库了但没人用（F2） |
| **导演**（调度） | 回合调度 + 张力启发式 | 同上 + **收束时输出结构化事件摘要** | 收束产物没有结构化出口（F4） |
| **角色**（演绎） | think/decide，黑盒 | 不变——**这是核心资产，别动** | — |
| **成文**（渲染） | 150-220 字段落 | **场景级渲染器**：按章级目标分 3-5 段写满、段间承接 | 被降级（F1） |
| **责编**（连续性） | 场景级对话副驾 | 对话副驾 + **章后自动一致性巡检**（体检∥质检→裁决→自动记账） | 只做场景级、且要人工推（F5） |

### 3.3 建议：不加 agent，只把职责归位

**不新增席位**（现在 6 个 spec 已经够），要做的四件事：
1. 成文席从「一段」升级为「一场/一章」
2. 主笔的章级字段真正注入成文
3. 导演收束产出结构化摘要（事件/转折/张力）
4. 责编增加「章后自动巡检」跑法（复用现有审稿会编排，零新引擎）

> 反面做法（不做）：再加「审核官/润色官/世界观官」等 agents。席位越多，prompt 越难对齐，
> 而当前瓶颈是**没人把一章写完**，不是角色不够多。

## 4. 两种写作模式 + 「没有场景怎么办」

### 4.1 定义

| | A 涌现模式 | B 直写模式（**新增，保底**） |
|---|---|---|
| 输入 | 场景 + 角色卡 + 推演回合 | 章大纲 / 一句话方向（**无需场景**） |
| 流程 | 推演 → 收束 → 成文渲染 → 体检/质检 | 章级规划 → 分段落写满 → 体检/质检 |
| 产出 | 有「意外但成立」的桥段 | 稳、可控、按大纲推进 |
| 差异 | 产品的护城河 | 保证「不涌现也能交付」 |

**关键结构改动：把「章」变成最小可写单位，「场」是可选的细分。**
现在反过来——场是唯一可写单位，所以没场景就寸步难行。

### 4.2 「没有场景」的四种情况与对策

| 情况 | 现在 | 应该 |
|---|---|---|
| 只有一句话方向 | 只能先去主笔排骨架 | 允许直接写：主笔先出**章级三行**（这章要完成什么/基调/字数）→ 直写成文 |
| 有章但没拆场 | 无法写 | 直写以「章」为单位；拆场是可选项（写完再拆/边写边拆） |
| 有场但设定空 | 照写（质量差） | 写前自动补设定（主笔/责编生成 stage_desc/goal），或明确降级为「直写」 |
| 推演失败/无 LLM | 回退到确定性脚本 | 直写模式兜底 + 明确提示「本次未涌现」 |

### 4.3 前端的对应改动（C 端视角）

写作页必须有两态：**有场 → 场景视图**；**无场 → 章视图**（同一编辑器，切换粒度）。

## 5. 涌现：怎么提升、怎么评测

### 5.1 提升（4 个杠杆，按投入产出排序）

1. **提高推演产物的利用率**（F4）：把导演收束的事件流/转折/张力结构化喂给成文
   —— 现有 19 回合的资产只用了两小撮，这是**最便宜的一大步**。
2. **提高角色卡覆盖率**：新书还没角色卡，写手只能「按名字自设腔调」。骨架落库时自动生成角色卡。
3. **导演策略调参**：现有 `goal_pressure / env_pressure` 已是好起点；用评测指标回归调，而不是拍脑袋。
4. **收束质量**（设计稿 S3 说缺）：收束决定「这一场结束得漂不漂亮」，直接影响正文可读性。

### 5.2 评测（必须可复跑，否则「提升」是玄学）

- **过程指标（0-token，可算）**
  - 回合数、角色发言占比、事件数/转折数
  - 张力曲线形态是否按计划（raise/hold/release 的实测落点）
  - **意外率** = 角色决策偏离导演计划的回合占比（**这才是「涌现」的量化信号**，偏离过高=崩，过低=剧本化）
- **结果指标**
  - structure_score、体检问题数/高危数、质检风险数、评审总分、伏笔回收率
- **A/B 评测**：同一剧本 + 固定 seed 跑 N=5 次 → 指标分布（不是单次）
- **人工盲评**（3 人 × 5 分）：可读性 / 意外但不违和 / 角色可信度
- **基线快照**：每次调 prompt/策略后跑同一剧本，与基线对比（防止「越改越平」）

> 现状：只有 tension 启发式 + structure_score。**「涌现好不好」没有定义、没有基线、没有回归** ——
> 这是「涌现」作为护城河最危险的地方：无法证明它在变好。

## 6. 前端缺陷（C 端产品视角）

数据：主笔页 1391 行、人物 804、设置 520 —— 功能密度高，但**没有主线**。

| # | 问题 | 影响 |
|---|---|---|
| U1 | 5 个入口（主笔/导演/正文/概览/校对）平级并列 | 作者不知道「下一步点哪」 |
| U2 | 写作页无场景即空态死路 | 新用户第一屏就卡住 |
| U3 | 场景设定空着也能写，无「写前检查」 | 产出必然被体检打回 |
| U4 | 章级目标（word_target/tone）不显示 | 作者不知道这一章要写多少字 |
| U5 | 没有「一本书的完成度」仪表（章数/字数/进度%） | 没有长跑目标感 |
| U6 | 工具结果/审计信息过载 | v1.43/v1.44 已改善（明细富卡+可收起），继续收敛 |
| U7 | 设置页 520 行、人物页 804 行 | 工具页比主线页更重，优先级倒挂 |

**建议**：新增一个**「写作主线」视图**（书→章→场，带完成度、字数、下一步按钮），
其余页面降级为「工具页」。C 端产品的第一屏应该是「你的书现在到哪了、下一步做什么」。

## 8. RAG 的定位（回答「下一步是不是 RAG」）

**不是第一步，但接口现在就该留。**

- 现在全书 286 字，检索零收益；**先解决「写不满、串不起」**。
- 但等写到 10 章再改架构成本更高 → 现在把 `memory.search(query)` 做成**工具**（走现有 ToolExecutor），
  底层先用「0-token 关键字 + 结构化筛选」（账本/伏笔/摘要表都是现成的），
  验证「按需检索真的有用」后，再把你那份 RAG 库作为**向量后端**插进去。
- **索引对象必须是摘要，不是裸正文**（场景摘要/章摘要/伏笔-场景映射），否则检索出来的是一堆无关片段。
- 接入前需要你确认：你的库是什么栈（Python? 独立服务?）、向量库是不是 pgvector（我们已有 PG16+pgvector）、
  检索接口形态（search(query, top_k) 返回什么 metadata）。

## 9. 下一阶段路线图（先修流程，再谈功能）

## 10. 需要你拍板的三件事

1. **主线单位**：认可「章是最小可写单位、场是可选细分」吗？（这是 P0 的结构前提）
2. **两条腿的优先级**：先 A 涌现模式，还是先 B 直写模式？
   我的建议：**先 B（保底能用）再 A（差异化）**——因为 B 能最快产出「一章」，A 才有可对比的基线。
3. **RAG 库**：把仓库路径/技术栈给我，我先评估接入成本（不接，只出评估）。
