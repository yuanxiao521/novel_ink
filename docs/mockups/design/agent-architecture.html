SupervisorAgent（副驾）

理解意图 → 决定要不要动手 → 选工具与顺序 → 汇报结果（可解释）
输出结构：{ reply, actions: [{ tool, args, why }] }

落地方式（关键取舍）：现有 LLM 客户端只有 call_strong(prompt, json_schema) + response_format=json_object，没有 function calling。 所以第一版走 「计划式工具调用」：模型只出 actions[] JSON（用现有 schema_retry 校验纠错），由本地 ToolExecutor 执行 —— 可测、可审计、FakeLLM 就能跑；真 function calling 等需要多轮探索时再上。

为什么"按钮 = 工具"必须统一

同一份实现 → agent 不会发明按钮没有的能力
同一套审计 → 事后能查"这改动是谁让做的"
同一道闸门 → 落库/落账/删除，点按钮和让 agent 做一样安全
测试只需测一层：ToolExecutor + Registry（FakeLLM 可全绿）

段落序号 + 批注（要新增的数据）

段落序号 ¶1 ¶2 ¶3 —— 前端按空行切段即可，0 新增字段；作为 agent 的定位锚
批注 建议落库（否则刷新丢）：新表 prose_annotations（scene_id / 段落号 / 引用原文 / 作者意见 / 状态 / 时间）
选中工具条：批注 · 问副驾 · 让写手重写这段 · 标记保留
闭环：批注 → 副驾读 → 调 prose.draft/polish → 出 diff → 作者采纳

副驾的边界（避免"AI 乱改"）

read 类工具：随便调，不落库
write 类（初稿/润色/定点修复）：只出候选 + diff，采纳才写
destructive（保存/落账/删除）：必须显式确认
事实不可变：沿用现有 fact_gate（专名/数字/术语/台词逐字）
这一层现在缺什么
· 没有工具注册表：7 个按钮各自直连 service，行为散落
· 没有对话入口：正文页只能点按钮，作者"说不清但看得出不对"时无处表达
· 没有批注：选中一句话只能自己改，agent 不知道作者在意什么
