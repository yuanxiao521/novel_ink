墨卷 · Agent 五模块 × 通信三层（现状 vs 目标）

照代码核对：感知只有角色 agent 做对了（视角隔离）；通信是"靠环境痕迹协作"，缺显式消息层

一、每个 Agent 应有的五模块现状打标

① 感知（Perception）perceive角色：有
唯一做对的样板：character.perceive_context(char_id) —— 只给该角色子集（自我认知 / 已知信念近 5 条 / 可见度裁剪的事实 perceivable_facts / 近况 6 条事件），视角隔离是铁律。
其余 agent 全是全量注入：主笔（书树+记忆全量）、写手（场景+角色卡全量）、体检/润色/质检（正文全量）。其余：无独立感知模块
② 记忆（Memory）memory有账本 · 无分层
现有四堆东西混用：
· 书级记忆 book_memories（主笔独享）
· 三本账 beliefs/world_states/foreshadows（角色读裁剪视图，写手全量注入）
· 回合史 TurnArchive（含思考档）——只在导演台/剧本台读，正文协作完全不读
· 审计 prose_notes——只给人看，agent 不读
缺：短期记忆（对话史只有主笔有 chat_histories）、工作记忆（本场正文+批注+本轮工具结果）
③ 上下文装配（Context）compose无统一装配器
四层 Prompt 模板（作者要求 → 世界观 → 感知现场 → 任务）只在角色 agent 落地（_compose_prompt）；其余 agent 各自硬编码拼字符串：_DRAFT_PROMPT/_REVIEW_PROMPT/_VERIFY_PROMPT/chief_perceive。
后果：每加一个 agent 就复制一遍拼装逻辑，"它到底看到了什么"无法断言
④ 执行（Action）execute有校验 · 无工具层
现在 = 返回结构化 JSON + schema_retry 纠错 + service 落库（算是执行层的雏形）。
缺：ToolRegistry / ToolExecutor（上一轮已定）—— 工具声明、副作用等级、确认闸门、审计归因
⑤ 功能边界（Boundary）spec隐性约定
靠"谁能读什么"的口头约定 + 0-token 护栏（world_rules/guard）+ 事实闸门兜底。
缺：显式能力声明（能读什么 / 能写什么 / 能用哪些工具 / 模型档位 / 产出哪些事件）

二、Agent 间怎么通信：三层现在是 2 层

L1 黑板层 · 回合内turn-local · 内存已有
SimulationState 就是黑板对象（LangGraph State 持 sim，节点内原地改）：导演写引导 → 角色读 → 角色 act 写事实 → 刷新世界 → 成文。节点顺序执行 = 隐式同步。
要补：字段级写权限（谁能写哪个字段）
L2 账本层 · 跨场景 / 跨会话durable · DB已有
事实与状态：三本账 + 世界状态 + 书级记忆 + 回合归档 + 审计。传递方式是 "落库 → 再装配 prompt"——即 通过数据库中介的间接通信（stigmergy，蚂蚁靠信息素）。
优点：可审计、可回放、崩溃可恢复。缺点：延迟高、不能"问一句"、不能协商、能力无法被发现
L3 消息层 · 显式请求-应答★ 缺没有
现在没有任何 agent 直接问另一个 agent。但要落地这些诉求就必须有：
· 责编："这场我没把握，请求彩排" → 派给导演
· 写手："信息曝光不足" → 请求补事实
· 质检："这条风险我判不了" → 请求作者裁决
建议落两张表：agent_tasks（谁发起/给谁/目标/输入引用/状态/产物引用）+ agent_messages（request/response/notify）
A2A 要分清两件事：
协议（Google 提 / 现归 Linux Foundation）解决的是跨进程、跨厂商互操作 —— Agent Card（能力发现）、Task（带状态机的长任务）、Message/Part、Artifact、SSE 流式事件。我们单进程、同库，不需要上 HTTP/JSON-RPC 那套重传输。
但它的数据模型值得抄：AgentCard→AgentSpec、Task→agent_tasks、Message→agent_messages、Artifact→现有产物（骨架/TurnArchive/final_prose/prose_notes 已经是 artifact，只差登记到任务单）
结论：借模型，不借传输。

三、目标记忆分层（建议）

层生命周期谁写谁读
短期回合 / 本轮对话各 agent 自己仅自己
工作记忆场景ToolExecutor / 作者批注责编 · 写手
长期事实书（跨场景）记账 agent全员读裁剪视图
约束与偏好书主笔 / 作者全员读（B 批：约束表全局化）

四、差距与落地顺序

模块现状归属批次
感知仅角色有B：统一 perceive(scope) → 结构化感知包
记忆有账本无分层A 工作记忆（批注落库）+ B 四层
上下文无统一装配器B：感知包 → 各自模板渲染
执行schema 校验，无工具层A：ToolRegistry + ToolExecutor
边界隐性约定A+：AgentSpec 能力声明
通信黑板 + DB 间接（2 层）A+：消息层 + 任务单；C 首次实战（请求彩排）
不要一次改 7 个 agent：先给两个样板落地五模块 —— 主笔（结构层样板） + 责编（场景层样板），跑通再推广，否则 7 处同时改无法归因。
